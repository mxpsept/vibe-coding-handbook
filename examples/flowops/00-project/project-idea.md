# FlowOps — Project Idea

> Status: Reviewed teaching baseline for Gate 0
>
> Case: FlowOps / Northstar Group（完全虚构）

## 1. Background

Northstar Group 是一个约 3,000 人的虚构中大型企业，组织形态包含总部和多个业务部门。企业存在跨部门重点工作，并通过经营会议、专项会议等方式持续推进部分周期较长的任务。

当前重点任务大量依赖 Excel、即时通讯、邮件和会议进行跟踪。随着任务数量和协作范围增加，团队开始考虑是否需要一种统一的数字化方式改善重点任务督办。

## 2. Problem Statement

当前重点任务的信息分散在 Excel、即时通讯、邮件和会议中，导致责任关系、进展、截止时间和历史过程难以形成统一视图。

督办人员需要通过人工方式持续询问和汇总进度，临期或超期事项可能被较晚发现；管理者也难以快速获得整体执行情况。

团队希望进一步确认这些问题的真实程度、影响范围和优先级，并判断建设重点任务督办平台是否是值得投入的解决方向。

## 3. Target Users / Stakeholders

以下均为 Stage 00 初始假设，必须在 Discovery 中验证。

| Stakeholder | Current assumption | Why relevant | Need to validate |
| --- | --- | --- | --- |
| 管理者 | 需要了解重点任务整体执行与风险 | 可能是管理视图主要使用者 | Yes |
| 督办人员 | 负责创建、跟踪、催办和汇总重点事项 | 可能承担最高频业务操作 | Yes |
| 部门负责人 | 接收部门任务并协调执行 | 可能连接任务下达与实际办理 | Yes |
| 执行人员 | 负责实际办理和进展反馈 | 可能是进度数据主要来源 | Yes |
| 系统管理员 | 维护组织、用户和权限 | 企业系统通常需要基础治理角色 | Yes |

## 4. Known Facts

根据当前案例基线，已知：

- Northstar Group 为约 3,000 人的虚构中大型企业；
- 企业存在总部和多个业务部门；
- 存在跨部门重点工作；
- 管理层定期召开经营和专项会议；
- 部分重点任务持续数周或数月；
- 当前大量使用 Excel、邮件和即时通讯协作；
- 已观察到任务来源分散、Excel 版本难统一、责任关系不清、进度需要人工询问、临期事项发现较晚、超期催办记录不统一、管理层缺少整体视图以及历史过程难追溯等问题。

## 5. Assumptions

以下内容目前只是候选假设：

- “统一督办平台”可能比继续优化 Excel 流程更适合解决问题；
- 管理者可能需要 Dashboard 或驾驶舱；
- 督办人员可能需要统一创建和下达事项；
- 执行人员可能需要主动填报进展；
- 系统可能需要临期 / 超期提醒；
- 系统可能需要催办记录；
- 企业可能需要任务办结流程；
- 组织、用户、角色和权限可能需要进入 MVP。

这些内容均不得在 Discovery 前升级为最终 Requirement。

## 6. Unknowns

当前至少存在以下关键未知项：

- 哪些类型的工作真正属于“督办事项”？
- 谁可以创建和下达督办事项？
- 是否存在统一的任务来源分类？
- 下达后是否需要签收或确认？
- 责任部门、责任人和协办方如何定义？
- 进度由谁更新，多久更新一次？
- “临期”如何定义？
- 超期以后当前真实处理方式是什么？
- 是否存在延期、变更、取消、核销等业务动作？
- “完成”与“办结”是否是同一个概念？
- 谁拥有最终办结权？
- 管理者真正需要哪些决策信息？
- 不同部门之间的数据可见范围如何界定？
- 当前 Excel / 即时通讯流程中最耗时的步骤是什么？
- 当前问题造成了多大可量化影响？

## 7. Expected Outcomes

当前阶段只定义业务结果方向，不承诺具体 Feature：

- 降低重点任务信息分散程度；
- 让任务责任关系更清晰；
- 提高任务进度透明度；
- 更早识别临期、超期或长期未更新等风险；
- 减少督办人员重复询问和人工汇总工作；
- 为管理者提供更及时的整体执行信息；
- 提高重点任务历史过程的可追溯性。

具体 Outcome Metric 在 Discovery / Requirements 阶段进一步定义。

## 8. Constraints

当前已知约束较少。

- 案例必须保持完全虚构，不使用真实企业、人员和内部数据；
- 最终方案应适用于典型企业任务督办场景，而非某一特定行业；
- 不为了展示技术而增加不必要的基础设施；
- 具体预算、交付周期、合规要求、部署环境目前均为 Unknown。

## 9. Risks

| Risk | Why it matters | Current evidence | Next action |
| --- | --- | --- | --- |
| 把“需要系统”误认为已经证明 | 可能直接进入错误 Solution | 当前只有问题描述，没有方案验证 | Discovery 比较现状改进与系统化方案 |
| AI 根据常见督办产品自行补业务规则 | 会制造伪需求 | 已存在大量 Unknown | 强制区分 Fact / Assumption / Unknown |
| 管理者需求压过执行人员真实工作流 | 可能得到好看的 Dashboard、难用的执行系统 | Stakeholder 尚未访谈 | 覆盖不同角色访谈 |
| MVP 过大 | AI 容易快速生成大量低质量功能 | 当前已有候选功能清单 | Requirements 阶段重新 Prioritize |
| 过早确定技术与 UI | 设计可能绑架业务发现 | 技术栈目前只是候选 | Architecture / UI 决策后移 |

## 10. Discovery Questions

1. 当前有哪些真实任务来源？各自占比和重要性如何？
2. 一条重点任务从产生到结束，当前实际经历哪些步骤？
3. 哪些角色在每个步骤中做什么决定？
4. 当前 Excel、即时通讯、邮件和会议分别承担什么作用？
5. 哪一步最耗费督办人员时间？
6. 哪些信息最容易丢失、过期或产生版本冲突？
7. 临期和超期目前如何发现和处理？
8. 执行人员为什么会不及时更新进度？
9. 管理者在周会或月度会议前最需要回答哪些问题？
10. 哪些业务规则因部门或任务来源不同而变化？
11. 如果不建设新系统，是否存在成本更低的流程优化方案？
12. 什么结果可以证明这次改进值得继续投资？

## 11. Decision

- [x] Enter Discovery
- [ ] Need more information
- [ ] Stop / Park

### Decision rationale

当前已经存在明确、可描述且具有企业普遍性的协作问题，同时仍保留大量尚未验证的业务假设。

这意味着项目已经具备进入 Product Discovery 的价值，但远未达到直接进入 Requirements、UI 或 Coding 的条件。

下一步应通过 Stakeholder Mapping、访谈和 As-Is Process 分析验证问题，而不是直接开发候选 MVP。
